# 🚀 Release Guide — Asseto Asset Management

This document describes the **step-by-step process** for creating and publishing a new release of Asseto to GitHub for the community.

---

## 📌 Versioning Convention

We follow [Semantic Versioning (SemVer)](https://semver.org/):

```
MAJOR.MINOR.PATCH
```

| Increment | When to use |
|-----------|-------------|
| `MAJOR` | Breaking changes or major architectural shifts |
| `MINOR` | New features added in a backward-compatible manner |
| `PATCH` | Bug fixes, security patches, or small improvements |

**Examples:** `1.2.0` → `1.2.1` (patch), `1.2.1` → `1.3.0` (minor), `1.3.0` → `2.0.0` (major)

## ✅ Pre-Release Checklist

Complete **every item** before tagging a release.

### 1. Code Quality

- [ ] All feature branches merged into `develop`
- [ ] No open critical or high-priority bugs related to the release scope
- [ ] All Django migrations are up to date (`python manage.py showmigrations`)
- [ ] No debug code, `print()` statements, or `TODO` markers in release-scoped files
- [ ] `requirements.txt` is up to date

### 2. Testing

- [ ] Run the full test suite and confirm it passes:
  ```sh
  source env/bin/activate
  python manage.py test -v 2
  ```
- [ ] Manually verify core flows on the local dev server:
  - Login / Logout / 2FA
  - Asset create, assign, release
  - Gate pass creation and QR checkout
  - Vendor and product management
  - Upload (bulk import CSV)
  - Recycle bin restore
  - Notification delivery

### 3. Security

- [ ] No secrets, tokens, or credentials committed (check with `git log --all -p | grep -i secret`)
- [ ] No `.env` file committed
- [ ] Dependencies audited for known vulnerabilities:
  ```sh
  pip install pip-audit
  pip-audit
  ```

### 4. Documentation

- [ ] `README.md` is accurate and reflects any new features or changed setup steps
- [ ] `SECURITY.md` supported versions table updated if the MAJOR or MINOR version changes
- [ ] `CHANGELOG.md` entry written for this release (see format below)

---

## 📝 Writing a CHANGELOG Entry

Before tagging, add an entry at the **top** of `CHANGELOG.md` using this format:

```markdown
## [1.3.0] — 2026-06-15

### Added
- Gate pass QR code checkout support
- Support ticket improvements: priority labels and status workflow

### Changed
- Asset list page refactored for performance
- Role management UI redesigned for clarity

### Fixed
- Fixed session timeout not clearing cookies correctly
- Fixed organization isolation bug in audit log API

### Security
- Upgraded `django` to 5.0.4 to patch CVE-XXXX-XXXX
```

## 🔀 Release Branch Workflow

```
develop  ──────────────────────────────────────────►
              │                        ▲
              │ (cut release branch)   │ (merge back)
              ▼                        │
         release/1.3.0 ───── fixes ───►│
              │
              ▼ (merge to main)
            main  ──── tag: v1.3.0 ──►
```

### Step-by-step

```sh
# 1. Cut a release branch from develop
git checkout develop
git pull origin develop
git checkout -b release/1.3.0

# 2. Make any last-minute fixes on this branch only
#    (no new features allowed here)

# 3. Merge release branch into main
git checkout main
git pull origin main
git merge --no-ff release/1.3.0 -m "Release v1.3.0"

# 4. Tag the release on main
git tag -a v1.3.0 -m "Release v1.3.0 — <one-line summary>"

# 5. Push main and the tag to GitHub
git push origin main
git push origin v1.3.0

# 6. Merge the release branch back into develop
git checkout develop
git merge --no-ff release/1.3.0 -m "Merge release/1.3.0 back into develop"
git push origin develop

# 7. Delete the release branch
git branch -d release/1.3.0
git push origin --delete release/1.3.0
```

## 🏷️ Creating the GitHub Release

After pushing the tag:

1. Go to **GitHub → Releases → Draft a new release**
2. **Tag:** select `v1.3.0` (already pushed)
3. **Target:** `main`
4. **Title:** `v1.3.0 — <Short release title>`
   _Example: `v1.3.0 — Gate Pass QR & Support Ticket Improvements`_
5. **Description:** Paste the `CHANGELOG.md` entry for this version
6. **Assets:** Attach nothing unless explicitly needed (the source code zip/tar.gz is auto-generated by GitHub)
7. Tick **"Set as the latest release"** if it is a stable release
8. Tick **"Set as a pre-release"** only if it is a beta/RC
9. Click **"Publish release"**

## 🔖 Tag Naming Convention

| Type | Format | Example |
|------|--------|---------|
| Stable release | `v{MAJOR}.{MINOR}.{PATCH}` | `v1.3.0` |
| Release candidate | `v{MAJOR}.{MINOR}.{PATCH}-rc{N}` | `v1.3.0-rc1` |
| Beta | `v{MAJOR}.{MINOR}.{PATCH}-beta{N}` | `v1.3.0-beta1` |
| Hotfix | `v{MAJOR}.{MINOR}.{PATCH}` | `v1.2.1` |

## 🔥 Hotfix Release (Urgent Patches)

When a critical bug or security issue is discovered on `main`:

```sh
# Cut hotfix branch from main (NOT develop)
git checkout main
git checkout -b hotfix/1.2.1

# Fix the issue, commit
git commit -m "Fix: <short description>"

# Merge into main and tag
git checkout main
git merge --no-ff hotfix/1.2.1 -m "Hotfix v1.2.1"
git tag -a v1.2.1 -m "Hotfix v1.2.1 — <one-line description>"
git push origin main
git push origin v1.2.1

# Merge hotfix back into develop too
git checkout develop
git merge --no-ff hotfix/1.2.1 -m "Merge hotfix/1.2.1 into develop"
git push origin develop

# Clean up
git branch -d hotfix/1.2.1
git push origin --delete hotfix/1.2.1
```

## 📋 Post-Release Checklist

- [ ] GitHub Release is published and visible at `github.com/VyrazuLabs/asseto-asset-management/releases`
- [ ] `SECURITY.md` supported versions table updated if needed
- [ ] `develop` branch is up to date (release branch merged back)
- [ ] Team notified in Slack / communication channel
- [ ] Demo environment (`https://asset-management-hg2x.onrender.com`) updated if applicable

---

## ⛔ Rules — What NOT to Do

- **Never release directly from `develop` or a feature branch** — always use `main`
- **Never force-push `main` or `develop`**
- **Never reuse an existing tag** — delete and re-push is not acceptable; create a new patch version
- **Never include uncommitted changes or untracked files** in a release
- **Never add AI attribution** (e.g. `Co-Authored-By: Claude`) in release commit messages or PR bodies
